# passer-core

**Your devices, talking to each other — securely, directly, and only to each other.**

`passer-core` is the open core of [Passer](https://github.com/Walson-A/Passer): a small Rust
library that lets the devices of one person recognise each other, connect directly (or
through a relay that cannot read anything), and ask one another to do things — with a
permission check, a time-limited session and a local journal on the device that acts.

> Status: **prototype** (0.1). The protocol will change. Do not use it for anything that
> matters yet. Working name; the final name is not decided.

## What it does

| Layer | Crate | In one sentence |
|---|---|---|
| L0 Identity | `passer-identity` | Each device generates its own Ed25519 key; the public key *is* the device. The key stays in the system vault: DPAPI (Windows), Keychain (macOS, iOS), Secret Service (Linux), Android Keystore. |
| L1 Membership | `passer-membership` | A signed, hash-chained device log: only an existing approver can add a device, so a server that stores the log **cannot slip one in**. Pairing by one-time invitation link (QR) with a 6-digit check code. |
| L2 Transport | `passer-node` | [iroh](https://github.com/n0-computer/iroh) QUIC connections dialed by key: local network first, NAT traversal, relay as a fallback. End-to-end encrypted (TLS 1.3, raw public keys). |
| L3 Capability bus | `passer-bus` | Devices declare capabilities (schema close to MCP tools), as one-shot **calls** or as **streams** of bytes both ways (files, and later screens). Every call and stream goes through **one** checkpoint on the target: membership, input schema, policy (allow / ask / deny), human approval, visible indicator, lease (stop button), journal without content. |
| Server half | `passer-coord` | Coordination server: keeps each group's latest signed log and its devices' addresses and relays, so removals reach offline devices and devices find each other across networks; wakes a sleeping phone through a push gateway. Cannot add a device, never sees content, answers members only. Self-host it with the relay ([`docs/self-hosting.md`](docs/self-hosting.md)). |
| MCP bridge | `passer-mcp` | What your devices grant an AI agent, as MCP tools for Claude Desktop, Claude Code or Cursor (stdio). Agents get nothing until a device grants them a capability; each call is still checked, approved if needed and journaled on the device that acts. |
| Apps | `passer-ffi` | One `PasserDevice` object for apps, with Swift (iOS, macOS) and Kotlin (Android) bindings generated by UniFFI. The app provides the key vault, the approval prompt and its own capabilities as callbacks. See [`docs/platforms.md`](docs/platforms.md). |
| Modules | `passer-device-info`, `passer-files` | `device.info` (the smallest module, and the template for writing one: name, kind, system, versions). `file.drop` into an inbox, `file.list` and `file.get` from a shared folder, over streams: complete files only, names that cannot leave their folder. |
| Command over a stream | `passer-exec` | A stream capability that runs a command fixed by the host, its stdin and stdout wired to the stream (e.g. a screen-sharing helper). Only `{caller_name}` / `{caller_id}` are filled in; the process dies when the session ends. |
| Push gateway | `passer-push` | Wakes a sleeping phone (APNs for iPhone, FCM for Android) when the coordination server asks; runs next to it, holding the app vendor's push key. |
| CLI | `passer-cli` | `passer-core init / serve --invite --inbox --share / join / call / send / files / get / sync / remove / journal / grant / policy / mcp`. |

Runs on Windows, macOS and Linux (tested in CI) and builds for iOS and Android (CI).

What is **not** here, on purpose: screen capture and remote control (a separate project
that builds on this one), accounts, billing, the hosted service. See [`docs/architecture.md`](docs/architecture.md).

## Try it

```sh
cargo build --release
# first device
passer-core --home ./pc init --group Home --name PC
passer-core --home ./pc serve --invite            # prints a one-time join link
# second device (another terminal or machine)
passer-core --home ./laptop join '<link>' --name Laptop
passer-core --home ./laptop call PC device.info
```

Files, both ways:

```sh
passer-core --home ./pc serve --inbox ./Inbox --share ./Public
passer-core --home ./laptop send PC ./video.mp4           # lands in ./Inbox on the PC
passer-core --home ./laptop files PC                      # what the PC shares
passer-core --home ./laptop get PC notes.pdf --to ./notes.pdf
```

With a coordination server, devices find each other without knowing addresses:

```sh
passer-coord --home ./coord                      # prints --coord <id>@<ip:port>
passer-core --home ./pc --coord <id>@<ip:port> serve
passer-core --home ./laptop --coord <id>@<ip:port> call PC device.info
```

### Give an AI agent access to a device

```sh
# on the PC: allow the agent "claude", relayed by the laptop, to read device info
passer-core --home ./pc grant --agent claude --via Laptop --capability device.info --decision allow
```

Then point your MCP client at the bridge on the laptop, e.g. in Claude Desktop's config:

```json
{ "mcpServers": { "passer": {
    "command": "passer-core",
    "args": ["--home", "C:/path/to/laptop", "--coord", "<id>@<ip:port>", "mcp", "--agent", "claude"]
} } }
```

`--decision ask` makes the PC ask its user (or another approver device) at each use.

Both screens show the same 6-digit code at join time; if they differ, someone is in the
middle. `--network local` restricts to direct addresses; `--network relay --relay <url>`
uses a relay you run ([`docs/self-hosting.md`](docs/self-hosting.md)); the default `n0`
uses n0's public relays, which are for development only.

## Building on it

Experiments: yes, by git dependency or generated bindings. Products: not yet (0.x API, no
published packages, no external audit). What works and what is missing:
[`docs/integrating.md`](docs/integrating.md).

## Security

Security is the first priority of this project. The threat model, what is and is not
protected, and the known gaps of the prototype are in [`docs/security.md`](docs/security.md).
Tests, fuzzing and the results of the latest security review are there too.
To report a vulnerability, see [`SECURITY.md`](SECURITY.md) — please do not open a public issue.
